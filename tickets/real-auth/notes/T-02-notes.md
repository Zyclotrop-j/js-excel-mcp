## 1. Email-Optional User Schema Snippet (copy-paste-ready for T-20)

### 1.1 The mechanism — a custom plugin, NOT `user.fields.email`

**Finding (runtime-confirmed):** `BetterAuthOptions["user"]` does NOT expose a field-attribute override hook for core fields. The `user.fields` option is typed as `Partial<Record<Exclude<Keys, "id">, string>>` — it only **renames** columns (field name → column name string), it does not accept `DBFieldAttribute` objects. `user.additionalFields` is explicitly `Exclude<string, Keys | "id">` — it only adds NEW fields, not overrides existing ones.

Source: `node_modules/@better-auth/core/dist/types/init-options.d.mts` — `BetterAuthDBOptions<ModelName, Keys>` type (line ~"fields?: Partial<Record<Exclude<Keys, "id">, string>>").

### 1.2 The override path — a custom plugin's `schema.user.fields.email`

**Finding (runtime-confirmed by reading the compiled merge logic):** A plugin's `schema.user.fields` is spread AFTER the core user fields in `getAuthTables()`. The relevant merge order in `node_modules/@better-auth/core/dist/db/get-tables.mjs` is:

```js
user: {
  fields: {
    name: { type: "string", required: true, ... },
    email: { type: "string", unique: true, required: true, ... },   // ← core: required=true
    ...
    ...user?.fields,                                                 // ← plugin override spreads here
    ...options.user?.additionalFields
  }
}
```

A plugin's `schema.user.fields.email = { type: 'string', required: false, unique: true, ... }` REPLACES the core `email` field attribute set (the spread overwrites every key). This is the **only** supported way to make `email` nullable in better-auth 1.6.23.

### 1.3 The snippet T-20 must paste

```ts
// src/shared/emailOptionalPlugin.ts  (new file, created in T-20)
// Makes the core user.email column nullable while preserving UNIQUE.
// Verified against @better-auth/core@1.6.23 dist/db/get-tables.mjs:
// plugin schema fields spread OVER core fields, so this override takes effect.
//
// Spike-confirmed DDL output (npx @better-auth/cli generate):
//   create table "user" (..., "email" text unique, ...)   ← NO "not null"
import type { BetterAuthPlugin } from 'better-auth';

export const emailOptionalPlugin: BetterAuthPlugin = {
  id: 'email-optional' as const,
  schema: {
    user: {
      fields: {
        email: {
          type: 'string',
          required: false,   // ← overrides core's required: true
          unique: true,      // ← preserved (unique-where-not-null)
          fieldName: 'email',
          sortable: true,
        },
      },
    },
  },
};
```

Wire into `createRealAuth` (T-20) alongside the other plugins:

```ts
import { emailOptionalPlugin } from './emailOptionalPlugin.js';
// ...
plugins: [
  mcp({ ... }),
  passkey({ ... }),
  apiKey(),
  twoFactor({ ... }),
  magicLink({ ... }),
  emailOptionalPlugin,   // ← must appear in the plugins array; order does not matter
],
```

**Do NOT use `user: { fields: { email: { ... } } }` at the top level** — that option only renames columns and will silently do nothing for attribute overrides.

### 2.3 Notes T-12 must apply

- **`email TEXT UNIQUE`** (no `NOT NULL`) — Strategy A. SQLite allows multiple NULLs in a UNIQUE column (spike-confirmed in §3.3 below).
- **Table name is `apikey` (all lowercase, no underscore)** — NOT `api_key`. Confirmed by `API_KEY_TABLE_NAME = "apikey"` at `node_modules/@better-auth/api-key/dist/index-CI6mGUwK.d.mts:52` and the schema key at `index-CI6mGUwK.d.mts:1176`.
- **`apikey.referenceId` is the FK column** — NOT `userId`. When `references: "user"` (the default per `ApiKeyConfigurationOptions.references`), `referenceId` holds the user's id. T-30's token verifier must read `result.key?.referenceId` (NOT `result.key?.userId` — see §5.4).
- **`emailVerified` / `twoFactorEnabled` / `backedUp` / `enabled` / `rateLimitEnabled` / `verified` / `consentGiven` / `disabled` are `INTEGER`** — SQLite has no native BOOLEAN; better-auth stores 0/1.
- **`twoFactor` table stores BOTH the TOTP secret AND encrypted backup codes** in one row. There is no separate `backup_code` table. T-00 notes §3 said the same thing — this DDL confirms it.
- **No `rateLimit` table** — better-auth's rate-limit table is only created when `rateLimit.storage: "database"` is set. Our real-mode config does not set this (rate limiting is memory-only by default), so the table is omitted. If T-21 enables database-backed rate limiting, add the `rateLimit` table (key TEXT UNIQUE NOT NULL, count INTEGER NOT NULL, lastRequest INTEGER NOT NULL).
- **Per `AGENTS.md`**: when this schema changes, delete `data/_auth_real.db` before restarting (`CREATE TABLE IF NOT EXISTS` won't add columns to existing tables). Document in T-71.

## 3. Passkey-Only Signup Flow (copy-paste-ready for T-41)

### 3.1 API method names — verified against installed `.d.ts` (NOT the arch-decision doc)

**CRITICAL CORRECTION to `arch-decision-passkey-and-related.md` §1.5:** The passkey server API names listed there as `auth.api.addPasskey` / `auth.api.signInPasskey` **do not exist** in `@better-auth/passkey@1.6.23`. `grep` for `addPasskey` and `signInPasskey` in `node_modules/@better-auth/passkey/dist/index.mjs` returns **zero occurrences**. The actual endpoint property names (and thus `auth.api.*` method names) are:

| Operation | Correct `auth.api.*` name | HTTP route |
|---|---|---|
| Get WebAuthn registration options | `auth.api.generatePasskeyRegistrationOptions` | `GET /passkey/generate-register-options` |
| Verify registration response (store passkey) | `auth.api.verifyPasskeyRegistration` | `POST /passkey/verify-registration` |
| Get WebAuthn authentication options | `auth.api.generatePasskeyAuthenticationOptions` | `GET /passkey/generate-authenticate-options` |
| Verify authentication (create session) | `auth.api.verifyPasskeyAuthentication` | `POST /passkey/verify-authentication` |
| List user's passkeys | `auth.api.listPasskeys` | `GET /passkey/list-user-passkeys` |
| Delete a passkey | `auth.api.deletePasskey` | `POST /passkey/delete-passkey` |
| Update a passkey (rename) | `auth.api.updatePasskey` | `POST /passkey/update-passkey` |

Source: `node_modules/@better-auth/passkey/dist/index-Cyjp_etN.d.mts:260-771` — the `endpoints` object keys are the `auth.api.*` method names. **T-51's ticket body uses `passkey.register` / `passkey.verify` (wrong); the arch-decision doc's replacements `addPasskey` / `signInPasskey` are ALSO wrong. Use `verifyPasskeyRegistration` / `verifyPasskeyAuthentication`.**

### 3.2 The passkey-first signup call sequence

Passkey-only accounts (no email, no password) use `registration.requireSession: false` + `registration.resolveUser`. The flow T-41 must implement:

```ts
// ─── T-41 passkey-first signup (email = NULL, no password) ───────────────
// Pre-conditions: the auth_signup tool has, via elicitation, collected
// { name: string } from the user (email and password are omitted for
// credentialType === 'passkey'). The emailOptionalPlugin from §1.3 is loaded.

// Step 1: create the user row DIRECTLY via the internal adapter (no
// signUpEmail — signUpEmail requires email + password). email = null.
const internalAdapter = (auth as any).api?.adapter
  ?? (auth as any).options?.api?.adapter;  // structural escape, like auth.ts:267-283
const userId = (auth as any).api?.options?.database?.generateId?.({ model: 'user' })
  ?? crypto.randomUUID();
const now = new Date();
await internalAdapter.create({
  model: 'user',
  data: {
    id: userId,
    name: existing.name,         // from elicitation — z.string().min(1)
    email: null,                  // ← Strategy A: passkey-only account
    emailVerified: false,
    image: null,
    createdAt: now,
    updatedAt: now,
  },
});

// Step 2: get WebAuthn registration options. resolveUser (configured in
// createRealAuth) returns { id: userId, name: user.name } for the just-
// created row. The passkey plugin does NOT read user.email at this point.
const regOptions = await (auth.api as any).generatePasskeyRegistrationOptions({
  headers: new Headers(),       // no session — requireSession: false is set
  query: { name: 'default' },   // optional passkey label
});

// Step 3: return regOptions to the LLM/client. The client performs the
// WebAuthn ceremony in a browser/autofill context and returns a
// RegistrationResponseJSON. (T-41 surfaces this via a second elicitation
// round or a sampling round — T-41's design choice.)

// Step 4: verify the registration response. Stores the passkey row linked
// to userId. Returns the Passkey object (NOT a session).
const passkeyRow = await (auth.api as any).verifyPasskeyRegistration({
  body: {
    response: registrationResponseJSON,   // from the client's WebAuthn ceremony
    name: 'default',                       // optional label
  },
});
// passkeyRow: { id, name?, publicKey, userId, credentialID, counter, deviceType, backedUp, transports?, createdAt, aaguid? }

// Step 5: establish a session. Registration does NOT create a session;
// call verifyPasskeyAuthentication with the same credential. In practice
// the client immediately follows up with an authentication ceremony, OR
// (simpler for T-41) the server-side helper creates the session:
const authResult = await (auth.api as any).verifyPasskeyAuthentication({
  body: { response: authenticationResponseJSON },   // from a fresh WebAuthn ceremony
});
// authResult: { session: {...}, user: {...} } — session is now established.

// Step 6: store the session in the pending-login map (per [C-PL]) and
// return the loginNonce to the LLM. T-22's /sign-in consumes it.
```
